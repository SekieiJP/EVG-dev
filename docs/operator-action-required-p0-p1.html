対象: P0・P1改修を本番で有効にするための、FirebaseおよびGoogle Apps Script（GAS）への運用者作業です。実装の正系は Firebase Realtime Database（RTDB） であり、GAS + Spreadsheetは終了・中断済みゲームのアーカイブ専用です。GASの停止・設定不備で進行中ゲームが止まることはありません。

2026-07-29 現在、本番反映は未完了です。 GitHub Pagesはコミットfaebfc1のP0/P1 r2版を公開済みですが、本番RTDB Rulesは旧版です。実ブラウザのHistoryで historyPlayers: permission_denied と全員Skill 0表示を確認しています。 また、GAS archive URL/API keyは未設定です。Rulesの変更は共有本番セキュリティ境界への永続変更なので、 Codexへ実行を依頼する場合は「本番Firebase Rulesのデプロイを承認します」と明示してください。

2. Firebase RTDB Rules: バックアップとデプロイ

2-1. 現行Rulesを退避する

  1. Firebase Consoleでプロジェクト elevator-game-live を開き、Realtime DatabaseのRulesタブを開く。
  2. 現在有効なRules全文を、日時・担当者が分かる承認済み保管先へ保存する。保存先は公開リポジトリやこのHTMLではなく、運用上の安全な場所にする。
  3. 保存したRulesを復旧用として識別できる名前にする（例: 日時を含むファイル名）。

CLIを利用できる場合は、出力先が安全な保管先であることを確認してから次の要領で取得して構いません。

firebase database:get /.settings/rules --project elevator-game-live

2-2. リポジトリのRulesをデプロイする

  1. firebase/database.rules.json が今回のリリース版であることを確認する。
  2. リポジトリのルートで次を実行する。
firebase deploy --only database --project elevator-game-live
  1. CLIのrelease成功を確認する。失敗時は次節の戻し方に従い、原因を解消するまでゲームを開始しない。
  2. ConsoleのRules表示で、新しいRulesに少なくとも completedGamePublicDetails、historyPlayers、nextGameConfigs、archive の定義があることを確認する。
  3. デプロイ日時、担当者、リリースコミットを運用記録へ残す。

2-3. allowlist済みHostでSkill backfillを1回実行する

  1. Rulesのrelease成功後、次ゲームを開始する前に、allowlist済みHostブラウザで最新公開版を強制再読み込みする。
  2. Host画面で通常のHost認証を1回行う。認証時に全resultsとroot playerを読み、空だったSkill履歴、room mirror、公開履歴、完了詳細をversion CAS付きの1回のmulti-location updateで揃え、meta.schemaVersionをfirebase-rtdb-v3-skill-historyへ更新する。成功後の認証では移行を再実行しない。
  3. Hostの通信ログにfirebase-backfill-skill-historyがあり、Rules errorがないことを確認する。
  4. History画面を別ブラウザで開き、historyPlayers permission_deniedが消え、6人の現在Skillが0以外で表示されることを確認する。
  5. Firebase Dataタブで、現ゲームの完了詳細が5ステージ、6人の履歴長が5件×5人・4件×1人になっていることを確認する。個人名とSkill値は公開の作業記録へ転記しない。
SKILL_HISTORY_AMBIGUOUS または SKILL_HISTORY_CONFLICT が表示された場合は、数値一致による自動推測をせず移行を停止しています。次ゲームを開始せず、Rulesを戻したり手動で履歴を書き換えたりせず、Firebase exportとHost通信ログを保全して開発担当へ渡してください。
backfill前に次ゲームを開始しないでください。旧room/rootのSkill履歴が空のまま新しい結果を確定すると、過去29件を含まない履歴がcanonicalとして保存される可能性があります。
Rulesはコードと一組です。Rulesだけを古いものへ戻すと、Hostの原子的な結果保存・次ゲーム開始・履歴表示が拒否されることがあります。復旧時は必ず「戻す対象のアプリ版」と「Rules版」の組を記録してください。

3. Host allowlistの確認

  1. 実際にHostとして使う端末・ブラウザプロファイルでHost画面を開く。
  2. 画面のinternal-statusから firebaseUid を確認する。まだ表示されなければ、匿名Authの初期化完了を待って再読み込みする。
  3. Firebase ConsoleのDataタブで、次のパスにそのuidが true として存在することを確認する。
rooms/elevator-game-live/roles/hosts/<firebaseUid>: true
  1. 未登録なら、既存の roles/hosts を置換せず、当該uidの子だけを true で追加する。
  2. Host画面を再読み込みし、internal-statusで認可エラーが出ず、設定の保存・開始操作が可能であることを確認する。

シークレットウィンドウ、ブラウザデータ消去、別ブラウザ・別端末ではuidが変わる場合があります。開催に使うHost環境ごとに確認してください。Hostパスワードの画面入力は誤操作防止であり、RTDB/GASの認可根拠ではありません。

4. GAS archive専用版のセットアップとWebアプリ配布

4-1. 対象Spreadsheetに紐づくApps Scriptを更新する

  1. アーカイブ先として運用するSpreadsheetを開き、拡張機能 → Apps Script を開く。
  2. リポジトリの gas/src/Code.gs を対象プロジェクトの Code.gs に反映する。
  3. 保存後、エディタから setupElevatorGameSheets を1回実行する。
  4. Googleが求める権限を確認して承認する。Spreadsheetへの書込みと、Firebase ID token / Host allowlist検証のための外部HTTPアクセス（UrlFetchApp）が必要である。
  5. Spreadsheetに config、save_data、stage_results、stage_settings、game_history、archive_log が作成または更新されたことを確認する。

setupElevatorGameSheets は必要なシートとヘッダを用意します。既存archiveデータを削除する操作ではありません。ただし本番Spreadsheetで初めて実行する前に、通常のSpreadsheetバックアップを作成してください。

4-2. Webアプリの新バージョンをデプロイする

  1. Apps Scriptでデプロイ → 新しいデプロイを選ぶ。
  2. 種類としてウェブアプリを選ぶ。
  3. 次のユーザーとして実行は、Spreadsheetへ書込む運用者アカウント（通常は自分）にする。
  4. アクセスできるユーザーは、HostブラウザがGoogleログイン不要で呼べる範囲（通常は全員）にする。公開アクセスにしても、archive APIはFirebase ID tokenの検証とHost allowlistの確認を通らなければ書込みません。
  5. デプロイし、/exec で終わるWebアプリURLを控える。テスト用の /dev URLは本番設定に使わない。
  6. デプロイのバージョン、日時、実行者を運用記録へ残す。

4-3. クライアント設定を更新して公開する

  1. game/assets/js/config.js の次の2項目に、運用環境で管理している値を設定する。実値をIssue、レビューコメント、このHTML、コミットメッセージには書かない。
FIREBASE_ARCHIVE_GAS_URL: "<GAS Webアプリの /exec URL>",
FIREBASE_ARCHIVE_API_KEY: "<GAS config シートの apiKey>",
  1. この設定は静的クライアントから送信されるため、API key単独を秘密の認可境界として扱わない。実際の書込み認可はFirebase ID tokenと roles/hosts/{uid} の照合で行われる。
  2. アセットquery versionを更新して、通常のGitHub Pages公開手順でこの設定を配信する。Hostブラウザでは強制再読み込みまたは新しい公開版を開く。
  3. 設定を反映したコミット、公開日時、GASデプロイ版を対応付けて記録する。

5. 実ブラウザでのarchive確認

本番イベントの本ゲームではなく、参加者に影響しない小規模な確認ゲームで実施してください。archiveは archiveId と gameId による冪等upsertなので、同じアーカイブの再送でSpreadsheetに二重行を作らない設計です。

  1. allowlist済みHostで、小規模な確認ゲームを最終結果まで完了する。
  2. Host画面の戦績アーカイブ → 現在ゲームを保存を押す。
  3. 表示が保存済みになり、エラーが空であることを確認する。
  4. Spreadsheetの archive_log に成功記録があり、save_data、stage_results、stage_settings、game_history に当該ゲームのデータがあることを確認する。
  5. 保存済み戦績を再集計を押し、GASの再集計応答が成功することを確認する。
  6. 既に 未完了 または長時間変わらない送信待ちのarchiveがある場合は、URL/API key/allowlistを直したうえで未完了を再送を押す。保存済みに変わり、同じ archiveId の行が重複しないことを確認する。

2026-06-12終了済みの本番ゲームはSkill backfill後に5ステージの完了詳細へ修復されます。GAS設定反映後、同じHost画面の現在ゲームを保存からこの保存済み現ゲームを送信できます。手動送信でも全resultsを再確認し、修復詳細をRTDBへ原子的に保存してから同じgameId/archiveIdでGASへ送ります。新しいゲームを作成する前に、表示が保存済みとなり、Spreadsheet側の5ステージを確認してください。

別ゲームのarchiveが送信待ちまたは未完了の間は、現在ゲームの保存を先に行わないでください。アプリもarchive_pendingとして拒否します。必ず追跡中ゲームの未完了を再送を完了し、保存済みになってから次のゲームを送信してください。retry対象gameIdが追跡状態と異なる場合はarchive_mismatchとして拒否されます。

再送の導線自体を事前検証する必要があり、未完了の実例がない場合は、本番イベントではない確認ゲームだけで一時的に無効なarchive URLを配信して失敗状態を作り、正しいURLへ戻して再送する方法があります。この確認は公開切替を伴うため、通常の変更管理・承認手順で行ってください。

archive送信に失敗しても、RTDB上の進行・Skill・完了履歴は正系として残ります。失敗状態はHostの「未完了を再送」で回復できます。SpreadsheetからRTDBへ戻す復元操作は通常運用に含めません。

6. 失敗時の戻し方と切り分け

症状確認・復旧
Rules deployが失敗するゲーム開始を止め、CLIのエラーを解消する。緊急復旧が必要なら、2-1で保存したRulesをConsoleに戻して公開する。旧Rulesへ戻した場合は、そのRulesと互換なアプリ版へ戻すまでHostの書込み操作を行わない。
Hostが「allowlistに登録されていません」internal-statusの現在uidと rooms/elevator-game-live/roles/hosts/{uid} を照合する。uidの子を true で追加し、Host画面を再読み込みする。既存のhost uidを一括削除しない。
archiveが「GAS URL未設定」またはHTTPエラー/exec URL、Webアプリのアクセス範囲、公開済みクライアント設定を確認する。直せるまでURLを空に戻せばarchive呼出しは失敗状態になるだけで、ゲーム進行はRTDBで継続する。
archiveが「Firebase ID token」またはHost認可エラー匿名Authが有効か、Host画面を再読み込みしてtokenが更新されるか、GAS側のFirebaseプロジェクト/room設定とallowlistが一致するかを確認する。
archiveがarchive_pendingまたはarchive_mismatchRTDB archiveが追跡しているgameIdを変更・削除せず確認し、そのゲームの「未完了を再送」を先に完了する。別ゲームIDを手入力して再送しない。
GASがsetup_requiredを返す正しいSpreadsheetに紐づくスクリプトで setupElevatorGameSheets を実行し、必要シートが作成されているか確認する。
archiveを一時停止したい通常の公開手順で FIREBASE_ARCHIVE_GAS_URL を空にした版を配信する。RTDBのRules、進行データ、確定履歴を削除しない。復旧後はURLを戻して「未完了を再送」を使う。
