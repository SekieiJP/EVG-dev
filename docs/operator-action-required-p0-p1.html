  1. allowlist済みHostで小規模な確認ゲームを最終結果まで完了し、全ステージの得点、StageSkill、持ち点、現在Skillを確認する。
  2. 同日次ゲームでは直前ゲームの参加者が継続し、前日以前の参加者は退室状態になることを確認する。
  3. archive exportと現在ゲームを保存を確認し、RTDB完了詳細とSpreadsheetのステージ数が一致することを確認する。
  4. 既に未完了または長時間変わらない送信待ちのarchiveがある場合は、URL/API key/allowlistを直したうえで未完了を再送を押す。先行ゲームに続いて延期されていた後続ゲームも古い順に自動送信され、各archiveIdの行が重複しないことを確認する。
  5. 保存済み戦績を再集計を再度実行し、実ゲームでも成功することを確認する。
別ゲームのarchiveが送信待ちまたは未完了の間は、現在ゲームの手動保存を先に行わないでください。アプリもarchive_pendingとして拒否します。追跡中ゲームの未完了を再送すると、成功後に後続ゲームも古い順で自動送信されます。retry対象gameIdが追跡状態と異なる場合はarchive_mismatchとして拒否されます。

未完了の実例がない場合のretry smokeは、本番イベントではない確認ゲームだけで一時的に無効なarchive URLを配信して失敗状態を作り、正しいURLへ戻して再送できます。この確認は公開切替を伴うため、通常の変更管理・承認手順で行ってください。

archive送信に失敗しても、RTDB上の進行・Skill・完了履歴は正系として残ります。失敗状態はHostの「未完了を再送」で回復できます。SpreadsheetからRTDBへ戻す復元操作は通常運用に含めません。

6. 失敗時の戻し方と切り分け

症状確認・復旧
Rules deployが失敗するゲーム開始を止め、CLIのエラーを解消する。緊急復旧が必要なら、2-1で保存したRulesをConsoleに戻して公開する。旧Rulesへ戻した場合は、そのRulesと互換なアプリ版へ戻すまでHostの書込み操作を行わない。
Hostが「allowlistに登録されていません」可能なら既にallowlist済みのHostプロファイルを使う。新しいuidが必要なら追加対象の明示承認を得てから、internal-statusの現在uidとrooms/elevator-game-live/roles/hosts/{uid}を照合し、そのuidの子だけをtrueで追加する。既存のHost uidを一括削除しない。
次ゲーム・結果保存がrules_or_conflictで拒否される開いたままの旧タブを閉じ、公開済みr11を強制再読み込みする。履歴ノードやRulesを手動で緩めず、internal-statusのアセット版、roomVersion、lastRulesErrorを保存する。
現在ゲーム保存後も完了詳細が1ステージ次ゲーム操作を停止したままにし、元の4ステージresultsを変更せず、RTDB export、公開アセットversion、internal-status通信ログを保全して開発担当へ渡す。Spreadsheetの行を手動で複製して埋めない。
archiveが「GAS URL未設定」またはHTTPエラー/exec URL、Webアプリのアクセス範囲、公開済みクライアント設定を確認する。直せるまでURLを空に戻せばarchive呼出しは失敗状態になるだけで、ゲーム進行はRTDBで継続する。
archiveが「Firebase ID token」またはHost認可エラー匿名Authが有効か、Host画面を再読み込みしてtokenが更新されるか、GAS側のFirebaseプロジェクト/room設定とallowlistが一致するかを確認する。
archiveがarchive_pendingまたはarchive_mismatchRTDB archiveが追跡しているgameIdを変更・削除せず確認し、そのゲームの「未完了を再送」を先に完了する。別ゲームIDを手入力して再送しない。
GASがsetup_requiredを返す正しいSpreadsheetに紐づくスクリプトでsetupElevatorGameSheetsを実行し、playersを含む必要な7シートとヘッダが作成されているか確認する。
archiveを一時停止したい通常の公開手順で FIREBASE_ARCHIVE_GAS_URL を空にした版を配信する。RTDBのRules、進行データ、確定履歴を削除しない。復旧後はURLを戻して「未完了を再送」を使う。
