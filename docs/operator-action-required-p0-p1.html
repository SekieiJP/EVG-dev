  2. リポジトリの gas/src/Code.gs を対象プロジェクトの Code.gs に反映する。
  3. 保存後、エディタから setupElevatorGameSheets を1回実行する。
  4. Googleが求める権限を確認して承認する。Spreadsheetへの書込みと、Firebase ID token / Host allowlist検証のための外部HTTPアクセス（UrlFetchApp）が必要である。
  5. Spreadsheetに config、save_data、stage_results、stage_settings、game_history、archive_log が作成または更新されたことを確認する。

setupElevatorGameSheets は必要なシートとヘッダを用意します。既存archiveデータを削除する操作ではありません。ただし本番Spreadsheetで初めて実行する前に、通常のSpreadsheetバックアップを作成してください。

4-2. Webアプリの新バージョンをデプロイする

  1. Apps Scriptでデプロイ → 新しいデプロイを選ぶ。
  2. 種類としてウェブアプリを選ぶ。
  3. 次のユーザーとして実行は、Spreadsheetへ書込む運用者アカウント（通常は自分）にする。
  4. アクセスできるユーザーは、HostブラウザがGoogleログイン不要で呼べる範囲（通常は全員）にする。公開アクセスにしても、archive APIはFirebase ID tokenの検証とHost allowlistの確認を通らなければ書込みません。
  5. デプロイし、/exec で終わるWebアプリURLを控える。テスト用の /dev URLは本番設定に使わない。
  6. デプロイのバージョン、日時、実行者を運用記録へ残す。

4-3. クライアント設定を更新して公開する

  1. game/assets/js/config.js の次の2項目に、運用環境で管理している値を設定する。実値をIssue、レビューコメント、このHTML、コミットメッセージには書かない。
FIREBASE_ARCHIVE_GAS_URL: "<GAS Webアプリの /exec URL>",
FIREBASE_ARCHIVE_API_KEY: "<GAS config シートの apiKey>",
  1. この設定は静的クライアントから送信されるため、API key単独を秘密の認可境界として扱わない。実際の書込み認可はFirebase ID tokenと roles/hosts/{uid} の照合で行われる。
  2. アセットquery versionを更新して、通常のGitHub Pages公開手順でこの設定を配信する。Hostブラウザでは強制再読み込みまたは新しい公開版を開く。
  3. 設定を反映したコミット、公開日時、GASデプロイ版を対応付けて記録する。

5. 実ブラウザでのarchive確認

本番イベントの本ゲームではなく、参加者に影響しない小規模な確認ゲームで実施してください。archiveは archiveId と gameId による冪等upsertなので、同じアーカイブの再送でSpreadsheetに二重行を作らない設計です。

  1. allowlist済みHostで、小規模な確認ゲームを最終結果まで完了する。
  2. Host画面の戦績アーカイブ → 現在ゲームを保存を押す。
  3. 表示が保存済みになり、エラーが空であることを確認する。
  4. Spreadsheetの archive_log に成功記録があり、save_data、stage_results、stage_settings、game_history に当該ゲームのデータがあることを確認する。
  5. 保存済み戦績を再集計を押し、GASの再集計応答が成功することを確認する。
  6. 既に 未完了 または長時間変わらない送信待ちのarchiveがある場合は、URL/API key/allowlistを直したうえで未完了を再送を押す。先行ゲームに続いて、延期されていた後続ゲームも古い順に自動送信される。最後のゲームが保存済みに変わり、各 archiveId の行が重複しないことを確認する。

2026-06-12終了済みの本番ゲームはSkill backfillにより5ステージの完了詳細へ修復済みです。GAS設定反映後、同じHost画面の現在ゲームを保存からこの保存済み現ゲームを送信できます。手動送信でも全resultsを再確認し、修復詳細をRTDBへ原子的に保存してから同じgameId/archiveIdでGASへ送ります。新しいゲームを作成する前に、表示が保存済みとなり、Spreadsheet側の5ステージを確認してください。

別ゲームのarchiveが送信待ちまたは未完了の間は、現在ゲームの手動保存を先に行わないでください。アプリもarchive_pendingとして拒否します。ゲーム進行とRTDB完了履歴は継続でき、後続gameIdはFirebaseのキューへ保存されます。追跡中ゲームの未完了を再送すると、成功後に後続ゲームも古い順で自動送信されます。retry対象gameIdが追跡状態と異なる場合はarchive_mismatchとして拒否されます。

再送の導線自体を事前検証する必要があり、未完了の実例がない場合は、本番イベントではない確認ゲームだけで一時的に無効なarchive URLを配信して失敗状態を作り、正しいURLへ戻して再送する方法があります。この確認は公開切替を伴うため、通常の変更管理・承認手順で行ってください。

archive送信に失敗しても、RTDB上の進行・Skill・完了履歴は正系として残ります。失敗状態はHostの「未完了を再送」で回復できます。SpreadsheetからRTDBへ戻す復元操作は通常運用に含めません。

6. 失敗時の戻し方と切り分け

症状確認・復旧
Rules deployが失敗するゲーム開始を止め、CLIのエラーを解消する。緊急復旧が必要なら、2-1で保存したRulesをConsoleに戻して公開する。旧Rulesへ戻した場合は、そのRulesと互換なアプリ版へ戻すまでHostの書込み操作を行わない。
Hostが「allowlistに登録されていません」internal-statusの現在uidと rooms/elevator-game-live/roles/hosts/{uid} を照合する。uidの子を true で追加し、Host画面を再読み込みする。既存のhost uidを一括削除しない。
archiveが「GAS URL未設定」またはHTTPエラー/exec URL、Webアプリのアクセス範囲、公開済みクライアント設定を確認する。直せるまでURLを空に戻せばarchive呼出しは失敗状態になるだけで、ゲーム進行はRTDBで継続する。
archiveが「Firebase ID token」またはHost認可エラー匿名Authが有効か、Host画面を再読み込みしてtokenが更新されるか、GAS側のFirebaseプロジェクト/room設定とallowlistが一致するかを確認する。
archiveがarchive_pendingまたはarchive_mismatchRTDB archiveが追跡しているgameIdを変更・削除せず確認し、そのゲームの「未完了を再送」を先に完了する。別ゲームIDを手入力して再送しない。
GASがsetup_requiredを返す正しいSpreadsheetに紐づくスクリプトで setupElevatorGameSheets を実行し、必要シートが作成されているか確認する。
archiveを一時停止したい通常の公開手順で FIREBASE_ARCHIVE_GAS_URL を空にした版を配信する。RTDBのRules、進行データ、確定履歴を削除しない。復旧後はURLを戻して「未完了を再送」を使う。
