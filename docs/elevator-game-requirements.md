# エレベーターゲーム 要件定義書（ドラフト v1.23）

## 1. 概要

### 1.1 ゲーム概要
会場のスクリーンとプレイヤーのスマホを用いた、対戦型Webパーティゲーム。プレイヤーはエレベーターの「乗る階」「降りる階」を予測しながら投票し、複数ステージにわたる合計得点で順位を競う。

### 1.2 想定環境
- **ホスト**: PCブラウザ（メインスクリーン投影＋サブスクリーン操作）
- **プレイヤー**: スマホブラウザ
- **同時接続上限**: 100名
- **ルーム**: 単一ルーム運用

### 1.3 用語定義
| 用語 | 定義 |
|------|------|
| ゲーム | 複数のステージで構成される一連の対戦 |
| ステージ | N, X, P, Q とイベント設定からなる1試行 |
| チケット購入 | 乗車階・降車階・予想イベント回答を確定する投票行為 |
| 乗車成功 | ステージ(4)の人数判定をパスしてエレベーターに乗れた状態 |
| 強制下車 | 定員超過で当該階の乗客・乗車希望者全員が降ろされる状態 |
| 棄権 | 制限時間内にチケット購入を完了できなかった状態（0点） |
| ホスト | 進行操作権限を持つ運営者 |
| スクリーン端末 | メインスクリーン投影画面を表示する端末（ホストと同一可） |
| セーブデータ | UUID単位で永続化される、複数ゲームをまたぐ戦績データ |

## 2. ゲームルール詳細

### 2.1 基本ルール
1. 1階からN階まで昇るエレベーターがある。定員はX名。
2. プレイヤーは乗りたい階と降りたい階をひとつずつ選ぶ。
3. エレベーターは各階に止まり、**乗車処理 → 人数判定 → 下車処理** の順に進める。
4. 乗車処理でX名を超えた場合、その階の乗客・乗車希望者**全員**が強制下車となる。エレベーターは乗客0人で次階へ。
5. 得点計算式:
   ```
   素点 = 成功階数 × P - 申告階数 × Q
   最終得点 = 素点 + イベント加点・倍率による補正
   ```
- 成功階数・申告階数は、乗車階と降車階を両端含みで数える。例: 1階から10階までの場合は10階分、同一階指定は1階分。

### 2.2 入力制約
- 乗車階: 1〜N階の整数
- 降車階: 乗車階〜N階の整数（**下方向は不可**、**同一階は可**）
- 同一階指定の場合、乗車成功時は成功階数=1階（乗車階で人数判定通過→下車）と数える

> **補足**: 「同一階指定での成功階数=1階」は回答3の例（10階で乗車成功→同階下車=1階）に準拠する。

### 2.3 強制下車の挙動
- 同階で乗車申告したプレイヤーが複数いて、その合計が定員超過を引き起こす場合は**当該階の乗車希望者全員**がアウト。
- 強制下車に巻き込まれたプレイヤーは、強制下車が発生する前に人数判定を通過した階数分の上昇報酬を得る。
- 当該階で新たに乗ろうとして強制下車になったプレイヤーは、人数判定を通過していないため成功階数=0。
- 強制下車後、エレベーターは乗客0で次階へ移動を継続する。

### 2.4 「乗車できなかった」場合の得点
- 強制下車・禁止階指定などで乗れなかった場合も、申告に対する**Q倍ペナルティ（チケット代金）は支払う**。
- 禁止階指定などで一度も乗れなかった場合の得点式: `0 × P - 申告階数 × Q`
- 強制下車の場合の得点式: `強制下車前に人数判定を通過した階数 × P - 申告階数 × Q`

### 2.5 受付締切と二重操作防止
- チケット送信・棄権は、チケット購入受付中または締切カウントダウン中のみ受け付ける。
- 締切カウントダウン終了後は、遅延送信や再送信であっても新規のチケット送信・棄権を拒否する。
- ステージ集計は1ステージにつき1回のみ実行できる。重複した集計操作は拒否し、累積得点・Skill履歴の二重加算を防ぐ。
- ホスト進行操作は現在フェーズに合う操作だけを受け付け、範囲外の重複操作は拒否する。

## 3. イベント仕様

### 3.1 イベント種別
| ID | 名称 | 概要 | 設定パラメータ |
|----|------|------|----------------|
| E1 | 予想イベント | 試合中の事象を予想、正解で加点 | 問題文, 回答形式, 配点M, 不正解時点, 無回答時点 |
| E2 | 禁止イベント | S〜T階での乗降を禁止 | S, T |
| E3 | 倍率イベント | S〜T階での乗車成功点に倍率R | S, T, R |
| E4 | 特別階イベント | Y階で乗車成功していた場合に+M | Y, M |
| E5 | 人数指定イベント | A人以上乗車中の成功階に倍率R | A, R |
| E6 | 眺望イベント | 乗車成功した場合のみ、降車階×M を加点 | M |
| E7 | 入場料 | 棄権以外のチケット購入者全員に一律マイナスM点 | score=-M |
| E8 | 完乗ボーナス | 下車成功した場合に+M点 | score=M |

### 3.2 イベント適用ルール
- **倍率の合成**: 複数倍率が同じ成功階に重なる場合は**乗算**で合成（例: R=2 と R=3 → 6倍）。
- **適用対象**: 倍率Rは**乗車成功点（P側）にのみ**適用。Q倍ペナルティには適用しない。
- **計算順序**: 乗車成功点 × 倍率合成値 → イベント加点を加算 → Q倍ペナルティを減算。
- **E7入場料**: 棄権以外のチケット送信者に適用する。不正チケットや乗車不可でも購入者としてマイナスする。
- **E8完乗ボーナス**: ステージ結果の `status === "success"` のプレイヤーに適用する。
- **判定タイミング**: E4・E5は「2.1の(3)で乗車成功した瞬間に当該階にいた」かで判定。通過階での判定は行わない。

### 3.3 倍率イベントの粒度（2種類を独立実装）
- **E3a (区間倍率)**: S〜T階の成功階数のみに倍率を掛ける。
- **E3b (得点倍率)**: ステージの乗車成功点全体に倍率を掛ける（条件は別途指定）。

### 3.4 予想イベント（E1）詳細
- 1ステージあたり**最大2問**まで設定可能。
- 回答形式（4種類）:
  1. **整数入力**: `answerFormat: "integer"`（例: 強制下車は何回発生する？）
  2. **範囲選択**: `answerFormat: "range"` または `"select"`（例: 合計乗車人数は○〜○人）
  3. **プレイヤー指名**: `answerFormat: "player"` または `"player_uuid"`（例: 最高得点者は誰？）
  4. **Yes/No**: `answerFormat: "yesno"`（例: 全員が乗車成功する？）
- 択一式の未回答選択肢は「回答しない」と表示し、初期値にする。
- 配点（正解時加点M、不正解時点、無回答時点）はイベントごとに設定。
- 正解は `metric` または `answerMetric` で以下のゲーム結果メトリクスから自動判定する。
- `correctAnswer` は固定正解や暫定設定用のフォールバックであり、`metric` / `answerMetric` が指定されている場合はゲーム結果メトリクスを優先する。
- `forcedOffCount`: 当該ステージの強制下車発生回数。
- `totalBoarded`: 当該ステージで乗車成功した人数。
- `allSucceeded`: チケットを送信した全員が乗車成功した場合に `yes`、それ以外は `no`。
- `topPlayer`: 予想イベント得点を加える前のステージ得点ランキング1位のUUID。予想得点そのものが正解を変える自己参照を避ける。
- 範囲選択は `options` / `choices` / `ranges` のいずれかで選択肢を指定する。各選択肢は `value`, `label`, `min`, `max` を持てる。数値メトリクスの正解値が `min` 以上 `max` 以下なら正解とする。
- プレイヤー指名は現在参加中のプレイヤー一覧からUUIDを送信する。

### 3.5 禁止階のバリデーション方針
- UIでは送信前に**警告ダイアログを表示**。
- プレイヤーがOKを選択した場合は警告を無視して送信可能（戦略的に禁止階を選ぶ余地を残す）。
- 禁止階を指定して投票した場合、その投票は無効化され「乗車できなかった」扱い（Q倍ペナルティのみ発生）。

## 4. アーキテクチャ

### 4.1 全体構成
```
Host / Screen / Player browser
  └─ Firebase Web SDK ──► Firebase Authentication + Realtime Database
                                    │
                                    └─ final / 中断時のみ ──► GAS + Spreadsheet archive

* 本番中の正系（Single Source of Truth）はFirebase Realtime Database（RTDB）である。
* GASとSpreadsheetは進行中の状態を読書きせず、確定済みゲームのアーカイブ先だけを担う。
* ホスト端末とスクリーン端末は同一端末でも別端末でも運用可能。BGM/SE再生はスクリーン端末のみ。
```

### 4.2 構成要素
| 要素 | 採用技術 | 役割 |
|------|----------|------|
| 配信 | 静的HTMLホスティング（GitHub Pages等） | クライアントSPA配信 |
| クライアント | HTML/CSS/JavaScript（フレームワーク選定要） | UI・アニメーション |
| 認証 | Firebase Authentication | 匿名ログイン。Hostはuid allowlistで認可 |
| 正系データストア | Firebase Realtime Database | 進行、投票、結果、現在Skill、次ゲーム設定、公開戦歴 |
| 認可 | Realtime Database Rules | 役割・フェーズ・本人ノード単位の書込み境界 |
| アーカイブ | Google Apps Script + Spreadsheet | 終了/中断済みゲームの冪等な書き出しのみ |
| 通信方式 | RTDBの役割別リアルタイム購読 | 必要な小ノードを購読し、HTTPポーリングしない |

### 4.2.1 クライアント接続設定
- Firebase Web設定（API key、authDomain、databaseURL等）は静的クライアントのビルド時定数として埋め込む。Web API keyは公開識別子であり、権限保護には使わない。
- プレイヤーやHostが実行時にRTDB URLやGAS URLを入力する運用にはしない。
- ローカル検証はFirebase Emulator Suiteまたは明示的なFirebase mockを使用する。localStorageのルームは本番進行の代替にしない。
- GASアーカイブURLはHostだけが利用する設定とし、Player/Screenの通常経路からは呼ばない。
- `v=player`、`view=player`、またはURLパラメータなしで開いたPlayer入口では、同一画面内のHost/Screenタブへ遷移できない。Host/Screenは専用URLから開く。

### 4.3 状態管理方針
- **Single Source of Truth はRTDB** とする。クライアントは役割別の小ノード購読から表示モデルを作り、進行中room全体をlocalStorageへ保存しない。
- Host、Player、Screenは `public`、現在ステージ設定、必要な本人/投影用データをRTDB購読で自動追従する。HTTPの定期ポーリング、GAS `/api/status`、同一端末 `BroadcastChannel` 同期は本番経路に使わない。
- `public` のフェーズ遷移はHost allowlist uidだけが実行できる。クライアントは読取り時の `expectedPhase` と `roomVersion` を添えて変更を作り、Rulesが既存値に対する正しい次フェーズと `roomVersion + 1` を検証する。競合時は書込み全体を拒否して最新 `public` を再取得する。Playerの「次へ」ボタンでフェーズを進めたり、ランキング画面に意図的に置き去りにしたりしない。
- Hostがステージ集計を確定するときは、RTDBルートを基準にした1回のmulti-location `update()` で、フェーズ、`results/{stageId}`、`scores/{uid}`、`playerStats/{uid}`、プレイヤー履歴、操作ログを原子的に一括反映する。フェーズを先に確定して副作用を後書きする二段階方式と、個別順次書込みは禁止する。Rulesのversion/phase検証または既存結果により拒否された場合はupdate全体が反映されず、二重集計を防ぐ。

### 4.4 RTDB購読と同期
- 全画面で `rooms/{roomId}` rootの購読は禁止する。Hostは `public`、設定、参加者、投票状況、結果等、Playerは本人ticket/結果/score、Screenは投影用集約結果だけを購読する。
- フェーズ通知はRTDB listenerを主経路とし、表示再描画で入力中フォームを失わないよう局所的に更新する。
- `roomVersion` はHostのフェーズcommitごとに増加する。Player自身のticketやプロフィール更新をversion比較で捨てない。

### 4.5 時刻同期
- `/.info/serverTimeOffset` を購読し、`Date.now() + serverTimeOffset` を補正済みサーバ時刻として使用する。
- Hostが書く `countdownEndsAt`、`movingEndsAt`、`animationStartedAt`、`revealEndsAt` はRTDB server timestampを基準にする。各端末は補正済み時刻でカウントダウンと演出を同期再生する。
- Rulesだけでは厳密なサーバ時刻締切を完全には検証できないため、Sparkでは時刻改ざん耐性はHost信頼の範囲とする。Blaze移行時のFunctions検証は未解決事項として扱う。

### 4.6 通信失敗時の挙動
- RTDB通信を伴う参加登録、復元、投票、棄権、Host操作、設定反映、戦績取得、アーカイブ要求では、画面上に待機表示を出し、同一操作の連打を防ぐ。
- **送信失敗（タイムアウト等）**: クライアントは自動リトライ（指数バックオフ、最大3回）。リトライはクライアント通信ログへ記録する。
- **制限時間内に送信開始したリトライ**: 締切後でも、設定されたロスタイム内だけ再送を認める。判定は補正済みサーバ時刻で行う。
- **制限時間内に送信できなかった**: 「棄権」を自動送信。
- **棄権送信も失敗**: ホスト側で**未着プレイヤーとして可視化**し、手動対応を促す。

### 4.7 セキュリティ・不正対策
| 対策 | 内容 |
|------|------|
| 締切後の改変防止 | Rulesで投票フェーズと本人ticketパスだけを書込み可能にする。Sparkでの厳密時刻検証は4.5の制約に従う |
| なりすまし防止 | Firebase Authの `auth.uid` と本人ノードを照合。UUIDは復旧・表示用IDとして扱う |
| 投票改ざん防止 | クライアントとHost集計関数で入力範囲・禁止階等を検証し、Rulesで他人ノード書込みを拒否 |
| ランキング集計の信頼性 | Sparkでは信頼済みHostの決定的集計を確定値とし、二重commitをRulesのphase/version CASと既存結果検証で拒否 |
| ホスト権限保護 | `roles/hosts/{uid}` allowlistをRulesで検証。パスワードUIは誤操作防止であり認可根拠ではない |
| スクリーンURL | 常時固定URL。投影専用のため認証なし（操作機能を持たない） |

## 5. プレイヤー識別とセッション

### 5.1 識別方式
- 初回アクセス時にFirebase Anonymous Authで `uid` を発行し、RTDBの書込み権限は常に `auth.uid` で判定する。
- 参加時に**名前**を入力し、復旧・表示用のゲーム内UUIDを `uid` と対応付ける。UUIDはlocalStorageに保管できるが、認可トークンではない。
- 名前の重複は不可（参加時に既存名と衝突したらリジェクト）。
- **統計集計はUUIDをキーとする**。名前は表示用属性であり、変更されても同一プレイヤーとして扱う。

### 5.2 再接続・引き継ぎ
- 同一ブラウザ: ローカルストレージのUUIDで自動再接続。
- 別ブラウザ・別端末: クライアントの**設定画面でUUIDを手動入力**することで引き継ぎ可能。
- 参加完了時に**自分のUUIDを画面表示**（コピーボタン付き）。

### 5.3 UUIDのエクスポート/インポート
- クライアントの設定画面に「データ引き継ぎ」機能を設置。
- **エクスポート**: 現在のUUIDをテキスト表示・コピー可能。
- **インポート**: 控えたUUIDまたは運営から提供されたUUIDを入力欄に貼り付けて引き継ぎ。
- Cookie/ローカルストレージが消失した場合のリカバリ手段として機能。
- 運営からのUUID提供フロー: ホストがサブスクリーンの参加者一覧から特定プレイヤーのUUIDを確認し、口頭・チャット等で本人に伝える。

### 5.4 名前変更
- クライアントの設定画面で名前変更可能。
- 変更は**次のステージから反映**。進行中のステージ表示は旧名のまま。
- 変更頻度の制限なし。**ステージ間に何度でも変更可能**。
- 重複チェックの対象は**現在有効なUUIDと現在の表示名の対応**とする。
- 名前変更により使われなくなった過去名まで衝突回避する必要はない。
- 実装上はRTDB root `players/{uid}` と `rooms/{roomId}/players/{uid}` のUUID・現在名対応で実現する。
- 過去履歴の表示名は**変更時点の名前**を保持（履歴の整合性確保）。
- 統計集計はUUIDキーのため、名前変更によって過去戦績が分断されることはない。

### 5.5 ゲームをまたぐ統計
- セーブデータはUUID単位で永続化。
- 複数ゲームをまたいだ現在Skill、参加ゲーム数、参加ステージ数、最高得点、強制下車回数、予想イベント正解率、優勝回数等を集計可能。
- 過去ゲームの戦歴一覧をプレイヤー画面・ホスト画面の両方から閲覧可能。

## 6. ホスト機能

### 6.1 アクセス制御
- **ホスト用URL**: 操作機能を提供。操作権限は `roles/hosts/{auth.uid}` のallowlistで認可する。
- **スクリーン用URL**: メインスクリーン投影画面のみを表示（**常時固定URL**、認証なし）。
- **ホストパスワードUI**: 必要なら誤操作防止のローカルUIロックとして表示できるが、認可根拠にはしない。Host uidは開催前にFirebase Console/CLIでallowlistへ登録する。
- **同一端末運用**: 1台のPCで両URLを別タブ・別ウィンドウで開き、片方をプロジェクター出力に割り当てる。
- **別端末運用**: ホストはノートPC、スクリーンは会場PC等、独立した端末で運用可能。
- **同時ホスト**: 同一ホストURLに2名程度まで同時接続を許容。

### 6.1.1 同時ホストの操作競合
- 同一アクション（締切・次ステージ等）が同時発生した場合、**最初の操作のみ採用**し、後発は拒否。
- 他ホストの操作開始を検知した時点で、競合する操作ボタンを**ロック**して後発操作の発生を予防する。
- 他ホストが行った操作は、サブスクリーン上でリアルタイムに可視化（例: 操作ログ欄に「ホストB が締切を実行」など）。

### 6.2 サブスクリーン（ホスト操作用）
#### 6.2.1 ゲーム設定の事前作成GUI
- 複数ステージを順序付きで作成。
- 各ステージに N, X, P, Q とイベントを設定。
- イベントの追加・並べ替え・削除。

#### 6.2.2 設定のインポート/エクスポート
- **エクスポート**: JSON形式で全設定をダウンロード。
- **インポート**: JSONをアップロードして読み込み。
- **部分インポート**: 個別ステージのみのインポートを可能とする。
- **スキーマバージョン**: JSONに `schemaVersion` を含め、将来の互換性を担保。

#### 6.2.3 進行管理
- ヘッダーには現在ステージの進行状況として「現在ステージ数/総ステージ数, 現在ステージ名」を表示し、その右に現在フェーズと参加人数を表示する。
- 参加者一覧と現在の入力状況（投票済み・未投票・通信エラー）。
- 各参加者のUUID表示（リカバリ提供用）。
- リアルタイムランキング表示。
- 進行操作は単一の「次へ」ボタンに集約し、現在フェーズに応じてステージ説明、受付開始、締切、結果発表、順位表示、次ステージ/最終結果へ遷移する。

#### 6.2.4 過去戦歴の参照
- UUID単位の累積戦歴閲覧。
- 過去ゲームの結果サマリと、特定プレイヤーの履歴抽出。

### 6.3 スクリーン端末（投影用）
#### 6.3.1 ゲーム進行フェーズ表示
| フェーズ | 画面内容 |
|----------|----------|
| 参加者受付中 | ルーム参加URL/QRコード、参加者リスト |
| ステージ説明 | 総階数、定員、上昇報酬、運賃とイベント詳細 |
| チケット購入受付中 | チケット購入人数の円グラフ、参加者数 |
| 締切カウントダウン | 15秒のカウントダウン演出 |
| 移動中 | 3秒間の移動中演出 |
| ステージ結果発表 | エレベーター上昇アニメーション |
| 中間ランキング | 累積順位とスコア差 |
| 最終結果 | 総合順位・表彰演出 |

#### 6.3.2 結果発表アニメーション
- エレベーターが1階からN階へ上昇する演出。
- 横画面投影を主対象とし、かごは固定表示、フロア表示がスクロールしてかごが上昇しているように見える演出とする。
- 現在到達している階より上の階の結果は非表示にし、上昇アニメーションに合わせて順次表示する。
- 強制下車階など結果を示す背景色・表示は、当該階に到達するまで出さない。
- 各階での乗車、乗車不可、乗車中、下車、強制下車をビジュアル化する。「待機」はスクリーン表示しない。
- 画面左から順に、階数、固定表示のエレベーターかご、プレイヤー状態を列として分け、かごとプレイヤー表示が重ならないようにする。
- プレイヤー名は先頭5文字まで表示する。
- 乗降や強制下車が発生する階では、スクロールを暫定的に1秒間停止する。
- 総階数が30F以上のステージでは、乗車・乗車不可・下車・強制下車・ボーナス確定のいずれも発生しない階の表示時間を通常階より70%短縮する。
- 画面下部にはプレイヤー別の現在スコアを表示し、各階到達ごとに更新する。
- スコア表示では、運賃は発表開始時に減算し、上昇報酬は各階到達時に加算し、ボーナスは獲得が確定した階で加算する。
- プレイヤースマホ側演出と**ローカル補正時刻で同期再生**。
- Host画面の結果発表Skip機能は提供しない。演出完了後、Hostが「次へ」を押して順位表示へ進める。
- 最終階の演出完了後、スクリーン端末では結果を振り返るために画面を自由にスクロールできる。
- 演出時間は実装後の調整事項。

#### 6.3.2.1 QRコード
- 参加者受付中のスクリーンでは、参加URLをQRコードとして表示する。
- QRコード生成ライブラリは静的配信元に同梱し、CDNへ依存しない。
- 同梱ライブラリの出典、バージョン、ライセンスはREADMEに記載する。

#### 6.3.3 BGM/SE再生
- **再生はスクリーン端末のみ**。プレイヤースマホでは音声を一切再生しない。
- 音声リソースは**静的配信元に同梱**（GitHub Pages等のリポジトリに配置）。
- 音声リソースは `game/assets/audio/` にmp3で配置する。ファイルが未配置の場合は再生せず、クライアントログに一度だけ記録する。
- BGMはフェーズごとに切り替え、現在フェーズのファイルをループ再生する。
- BGMファイル名: `bgm_lobby.mp3`, `bgm_stage_intro.mp3`, `bgm_voting.mp3`, `bgm_countdown.mp3`, `bgm_tallying.mp3`, `bgm_reveal.mp3`, `bgm_ranking.mp3`, `bgm_final.mp3`。
- SEファイル名: カウントダウン開始 `se_countdown_start.mp3`、購入締切 `se_countdown_end.mp3`、乗車成功 `se_board.mp3`、乗車中の上昇成功 `se_ride.mp3`、下車成功 `se_exit.mp3`、強制下車 `se_forced_off.mp3`。
- 結果発表SEは、スクリーン演出が当該階に到達した時点でタイムラインから発火する。`se_ride.mp3` は、1人以上が乗車中で、その階で新規乗車・下車・強制下車がない場合に鳴らす。
- ホストはサブスクリーンから音量調整・ミュート操作が可能。
- 音声ファイル差し替え機能は**初版では不要**（将来の検討事項）。

#### 6.3.4 スクリーン端末の起動
- スクリーン端末ではブラウザの自動再生制限により、初回操作なしに音声を再生できない。
- スクリーン用URLにアクセスした時点で、画面上に「準備完了」ボタンを表示し、**スクリーン端末側でクリック操作を要求**。
- クリックでオーディオコンテキストが起動し、以後ホスト操作によって音声再生可能。
- **再接続時**: 切断・再接続後も音声再生のため、再度「準備完了」ボタンのクリックを要求する。

### 6.4 締切処理
- ホストが「締切」ボタン押下後、スクリーンで**15秒カウントダウン**。
- カウントダウン中もプレイヤーは投票変更可能。
- 0秒時点で締切確定、以降の投票は拒否（ロスタイム除く）。
- 締切確定後、ギリギリで送信されたデータを受け取るため、3秒間「移動中…」を表示してから結果発表画面へ遷移する。
- スマホ画面でも締切状況がリアルタイムでわかるよう表示。

### 6.5 表示名・数値表示
- 人の目に触れる画面では、`N` は「総階数」、`X` は「定員」、`P` は「上昇報酬」、`Q` は「運賃」、`R` は「ボーナス倍率」と表記する。
- 眺望ボーナスは「眺望: 乗車成功時、降車階で得点+階数x2」のように、条件と加点を端的に表示する。
- 得点は整数で表示する。
- Skillは小数点以下2桁まで表示する。
- Player画面のスマホ縦表示では、総階数・定員・上昇報酬・運賃を1行4列で表示する。

### 6.6 ランキング表示
- 2ステージ目以降を含む中間ランキングでは、今ステージのランキングと全体を通してのランキングを左右に併記する。
- 最終結果では全体を通してのランキングのみを大きく表示する。

### 8.1 互換性方針
- `schemaVersion` で破壊的変更を管理（セマンティックバージョニング）。
- マイナーバージョン上げでは追加フィールドのみ。読み込み時に不明フィールドは無視。
- メジャーバージョンが上がる場合は変換ツールを提供。

### 8.2 サンプル同梱
- 短時間パーティ版（3ステージ・10分想定）
- 標準版（5ステージ・30分想定）
- 本格版（10ステージ・60分想定）

### 8.3 次ゲームへの移行
- ゲーム終了後、HostはRTDB `rooms/{roomId}/nextGameConfigs/{configId}` に事前登録したゲーム設定から次ゲームを選択して開始できる。Spreadsheetの `game_configs` はアーカイブ出力であり、進行時の読取り元ではない。
- `nextGameConfigs` は予定ゲームテンプレートの置き場であり、実際に進行したステージ設定を保存する `results` / archive payloadとは分離する。
- `status=ACTIVE` の設定だけをHost画面の次ゲーム候補に表示する。選択後も候補は再利用可能なテンプレートとして残す。
- 次ゲーム開始時は、直前ゲームで**開始日と同じ日本時間の日付**に少なくとも1ステージでチケット購入を完了したプレイヤーだけを、UUID・表示名・現在Skill値・Skill履歴を保ったまま現在ゲームの参加者として引き継ぐ。完全棄権だけのプレイヤー、および前日以前に最後に参加したプレイヤーは現在ゲームから退室させる。
- 日付は各ステージ集計時刻と次ゲーム開始時刻を日本時間（Asia/Tokyo）で比較する。日付をまたぐゲームでは、次ゲーム開始日と同じ日に集計されたステージへ参加したプレイヤーだけを引き継ぐ。
- 次ゲームではゲーム内累積得点、チケット、ステージ結果、現在ステージ位置はリセットする。
- 終了済みゲームの結果はRTDBの履歴ノードへ確定し、次ゲーム開始後も9項目の戦歴計算に含める。GASアーカイブの成功は次ゲーム開始の前提にしない。
- 参加者を破棄して完全に初期化する操作は、設定JSON importとは別のReset操作で行う。
- PlayerとScreenは `public.activeGameId` / `public.gameId` のRTDB購読で新ゲームを検出し、新しい現在フェーズへ自動追従する。

### 8.4 進行途中の中断と次ゲーム開始
- Hostは、少なくとも1ステージ分の集計済み結果がある場合、最終結果を待たずに現在ゲームを中断してRTDB `nextGameConfigs` の次ゲームへ移行できる。
- 中断時に保存する対象は、すでに集計済みの `stageResults` のみとする。未集計の投票、受付中・カウントダウン中・結果未保存の現在ステージ途中経過は保存せず破棄する。
- 中断保存されたゲームはRTDB履歴とGAS archive payloadへ確定し、サマリに `interrupted=true` と中断時フェーズを記録する。GAS書込み失敗時はRTDBのarchive statusを `failed` にして再送できる。
- 中断後の次ゲームでも8.3の当日参加判定を適用し、対象者のUUID・表示名・現在Skill値・Skill履歴を保持する。ゲーム内累積得点、チケット、ステージ結果、現在ステージ位置はリセットする。

## 9. Firebase command / query仕様

| 種別 | RTDB操作 | 概要 |
|------|----------|------|
| 時刻同期 | `/.info/serverTimeOffset` 購読 | 補正済みサーバ時刻を算出する |
| 状態購読 | `public` と役割別小ノード購読 | HTTP polling・全room取得を使わずに表示を同期する |
| Player command | `players/{uid}`、`tickets/{stageId}/{uid}`、`ticketPresence/{stageId}/{uid}` | 本人の参加、改名、投票、棄権のみ。Rulesで `auth.uid == uid` を必須にする |
| Host phase command | `public` を含むmulti-location update + Rules CAS | `expectedPhase` と `roomVersion` に相当する既存値検証をRulesで行い、次フェーズと時刻を確定する |
| Host result commit | `public`、`results`、`scores`、`playerStats`、履歴、`operations` の単一multi-location update | フェーズを含む同一ステージの結果・得点・Skill・操作ログを原子的に反映する。競合・既存結果はupdate全体を拒否する |

| 戦歴参照 | `completedGameSummaries`、本人詳細ノード | 公開サマリと本人だけの詳細を分離する |
| GAS archive | archive専用HTTP endpoint | final/中断後の確定payloadを冪等にSpreadsheetへ出力する。進行操作には使わない |

## 10.5 成績指標「Skill」

### 10.5.1 標準化得点
Skill計算ではプレイヤーの素点をそのまま使わず、ステージごとに**標準化得点**へ変換した値を用いる。

- 当該ステージ参加者の最低点を10、最高点を100に線形変換。
- **全員同点の場合は全員を55として扱う**。
- **参加者が1名のみの場合は標準化不能のため、当該ステージのSkill値は記録しない**。

```
StandardizedScore = 10 + (rawScore - minScore) / (maxScore - minScore) × 90
（minScore == maxScore のとき: 全員 55、参加者1名のとき: 算出しない）
```

### 10.5.2 ステージ別Skill値
各ステージ終了時、参加した全プレイヤーに対してSkill値を計算する。

```
StageSkill = (上昇成功階数 / (ステージ階数 × 定員 / 参加人数)) × 60
           + (標準化得点 / (参加者の標準化得点合計 / 参加人数)) × 40
```

- 計算結果が0未満になる場合は0にクランプ（最低値 = 0）。
- `参加者の標準化得点合計 == 0` の場合（参加人数0など特殊状況）は**第2項を0**とする。

| 変数 | 定義 |
|------|------|
| 上昇成功階数 | 当該ステージで人数判定を通過した階数。乗車階と降車階を両端含みで数える（1階→10階は10、同一階は1）。強制下車時は強制下車前に通過済みの階数。不参加・乗車失敗時は0 |
| ステージ階数 | ステージ設定のN |
| 定員 | ステージ設定のX |
| 参加人数 | 当該ステージで**乗車希望または予想回答のいずれかを送信したプレイヤー数**（完全棄権者は除外） |
| 標準化得点 | 10.5.1で算出した値 |

### 10.5.3 現在Skill値
プレイヤーが過去に参加した**全ステージ**のStageSkill値のうち、上位 1,2,3,4,5番目 の5つの値の合計。

- 参加ステージ数が5未満の場合は、不足分を0として加算する。
- 計算ロジックは今後変更の可能性あり。

### 10.5.4 表示する指標
プレイヤーの累積戦歴ページに以下を表示する。スマホ画面では優先度の高い指標を上部に固定し、残りは折りたたみで表示する。

| 指標 | 内容 |
|------|------|
| 現在Skill値 | 10.5.3の定義 |
| 平均Skill値 | 全ステージのStageSkillの算術平均 |
| 合計Skill値 | 全ステージのStageSkillの総和 |
| 最高得点 | ステージあたりの最高得点 |
| 参加ゲーム数 | 参加したゲーム数 |
| 参加ステージ数 | 参加したステージ数 |
| 強制下車回数 | 強制下車に遭遇した回数（自爆・巻き込まれを区別せず合算） |
| 予想イベント正解率 | 正解数 / **回答した予想イベント数**（無回答は分母に含まない） |
| 優勝回数 | ゲーム終了時に1位だった回数（参加人数による重み付けなし） |

### 10.5.5 集計タイミング
- 各ステージの集計直後に、StageSkillを計算・記録し、その値を含めて現在Skill（全StageSkillの上位5件合計）を更新する。更新後の現在SkillとStageSkill履歴は同一の結果commit multi-location updateでRTDBへ保存する。
- Skill履歴の二重適用判定はstageId単独ではなく、`JSON.stringify([gameId, stageId])` で表すゲーム単位のステージキーを使う。同じステージ設定を別ゲームで再利用した場合も、各ゲームのStageSkillを別実績として1件ずつ記録する。
- 旧データのSkill履歴がroot `players/{uid}` に存在する場合はrootをcanonicalとして保持し、room mirrorだけを同期する。root履歴が空で確定済み `results` にStageSkillが残る場合は、Hostによる移行時に現ゲームの全resultsと完了ゲーム詳細から有限値（0を含む）を時系列で復元し、root、`playerStats`、公開Skill index、完了履歴を1回のversion CAS付きmulti-location updateで揃える。roomにだけ由来不明の非空履歴がある場合や、同じゲーム・ステージの保存値が競合する場合は、数値一致で推測せず移行を停止する。
- ゲーム終了時には、更新済みの9指標をRTDB履歴へ確定し、GAS archive payloadにも含める。
- 個別ステージの結果はRTDBの `results` とプレイヤー本人の履歴ノードに保存し、Skill値の再計算に備える。戦歴閲覧時は保存済み値を読み出すのみ。
- 指標定義が変わった場合は、HostがRTDB履歴を対象に手動再集計を実行する。Spreadsheet関数は進行中・正系の再計算に使わない。

### 10.5.6 現在Skill値の配信と表示
- **表示位置**: タイトル画面および戦績ページにおいて、各プレイヤーの現在Skill値を表示する。
- **ゲーム中の表示**: ゲーム進行中は他プレイヤーのSkill値を参照しない（通信節約のため）。自分自身のSkill値のみ画面に表示する。
- **ステージ結果での表示と更新**: 結果発表解禁後のPlayer画面では、当該ステージのスコアとStageSkillを同じ結果カードに表示する。あわせて画面上部の本人の持ち点（ゲーム内累積得点）と現在Skillを、ステージ集計後の値へ更新する。
- **配信タイミング**: タイトル画面と戦績画面は公開プロフィールの現在SkillをRTDB購読で取得する。進行中はPlayer端末に本人分だけを購読させる。
- Player端末の個人戦績は画面キャッシュしてよいが、正系はRTDBであり、同一ゲーム・同一ステージの結果commit後はRTDB更新を反映する。
- Host/Screen端末はPlayerプロフィールの復元commandを実行しない。
- **更新タイミング**: 現在Skillは各ステージ集計後に更新し、Player端末は本人分だけを受信して表示する。ゲーム終了後も次回タイトル画面表示時にuid単位の最新値を取得する。
- **表示形式**: 小数2桁で表示。新規プレイヤー（参加ステージ数0）は `0.00`。
- **Skill値が計算されないステージ**: 参加人数1名のステージや全員同点でないが標準化不可能なエッジケースでは、当該ステージのStageSkillを記録しない。

## 11. 非機能要件

### 11.1 パフォーマンス
- RTDBのフェーズ反映は通常1秒以内を目標とする。HTTPポーリングを性能前提にしない。
- 100人同時アクセスでも、小ノード購読と投影用集約データによりRTDBの接続数・ダウンロード量の予算内に収まる設計にする。

### 11.2 可用性
- ホスト・プレイヤーともに再接続可能。
- RTDB接続障害時はクライアントにエラー表示しリトライする。GASアーカイブ障害はゲーム進行を停止させず、再送可能な失敗状態として残す。
- Host権限はFirebase AuthセッションとRTDB allowlistにより再判定する。token期限やGASパスワードへの再認証を進行条件にしない。

### 11.3 ブラウザ対応
- スマホ: iOS Safari 最新2バージョン、Android Chrome 最新2バージョン。
- PC: Chrome / Edge / Firefox / Safari 最新版。
- スクリーン端末: 上記PCブラウザに加え、HTML5 Audio APIが動作すること。

### 11.4 アクセシビリティ
- 色覚多様性に配慮した配色。
- 大きめのタップターゲット（最小44×44px）。

### 11.5 国際化
- 当面は日本語のみ。文言は別ファイル化して将来の多言語対応に備える。

### 11.6 ロギング・運用支援
不具合検証および運用のため、以下のログ・データ可視化を行う。

#### クライアント側
- **記録対象**: 画面上の情報に影響するすべての通信（リクエスト/レスポンス、ステート変更、エラー、リトライ）を記録。
- **保持件数**: ローカルストレージに直近一定件数を保持（具体的件数は実装時に決定）。
- **閲覧**: 設定画面の「通信ログ表示」から閲覧可能。
- **サーバ送信は行わない**。クライアントログはローカル閲覧のみとする。クライアント発の通信失敗はRTDBへ到達しないため、運営側はクライアント側のログを直接参照できない点に留意。

#### RTDB / Host側
- Host commandの成功・失敗を `operations` に記録し、Hostのinternal-statusでuid、phase、roomVersion、stageId、Rules error、archive statusを確認できるようにする。
- GASはarchive endpointの受付・upsert成否だけを実行ログに記録する。進行APIログは持たない。

#### スプレッドシート構成
SpreadsheetはGAS archiveの出力先であり、進行中room・次ゲーム候補・認可情報の正系ではない。アーカイブでは少なくとも次をupsertする。

| シート名 | 内容 | 主キー |
|----------|------|--------|
| `save_data` | プレイヤー単位×ゲーム単位の確定戦績（9指標、参加時表示名スナップショット） | (archiveId, UUID, gameId) |
| `stage_results` | プレイヤー単位×ステージ単位の確定結果（StageSkillを含む） | (archiveId, UUID, gameId, stageId) |
| `stage_settings` | 確定ゲームで使用したステージ設定 | (archiveId, gameId, stageId) |
| `game_history` | 確定ゲームの公開サマリ・中断フラグ | (archiveId, gameId) |
| `archive_log` | archiveId、要求/完了時刻、成否、エラー | archiveId |

### 11.7 データ保存方針
- セーブデータは複数ゲームをまたいで永続化。
- 1ゲーム終了または中断時にRTDBの確定payloadをGASへ送り、`game_history`、`save_data`、`stage_results`、`stage_settings`へ冪等にupsertする。
- `save_data` には参加時点の表示名をスナップショットとして保存する。正系のプロフィールはRTDB root `players/{uid}` であり、現在の表示名、現在Skill、StageSkill履歴を管理する。
- Playerの復帰は保存済み表示名で行い、復帰時の改名は行わない。復帰に失敗した場合は1回再試行し、失敗理由を表示したうえで新規参加フォームを表示し続ける。
- Player画面にはフェーズを先へ進める「次へ」操作を置かず、Firebase購読によりHostのフェーズ遷移へ自動追従する。
- 完了ゲームはRTDBでは公開一覧用の `completedGameSummaries` とHost詳細用の `completedGameDetails/{gameId}` に分割する。Player本人の個人戦績は `completedGamePlayerDetails/{uuid}/{gameId}` に本人分だけを保存し、公開ランキングと本人詳細を組み合わせて表示する。
- 結果発表演出は `animationStartedAt` と `revealEndsAt` をDBに保存し、Host再読み込み後も同じ演出完了判定を復元する。
- 最終ステージ後も `ranking` フェーズは経由するが、この画面では総合得点カラムを表示せず、ステージランキングだけを表示する。総合最終結果は次の `final` フェーズで表示する。
- Host、Screen、Player、Historyなど各画面の現在ゲーム表示では、RTDBの現在ゲーム参加者と8.3の当日参加判定で直前ゲームから引き継いだプレイヤーを表示する。前日以前に最後に参加したプレイヤーは自動コピーしない。
- 累積戦歴はRTDBのプロフィール・確定履歴から算出し、Spreadsheetは監査・外部保存用途に限る。

### 11.8 ゲームID
- **採番**: ホストが設定作成時に**任意に命名**（例: 「新年会2026」）。
- **重複時**: セーブデータに同名のゲームIDが既に存在する場合、**通し番号連番を付加**（例: 「新年会2026_2」「新年会2026_3」）。
- ゲームIDはRTDBの確定履歴とarchive payloadの主キーまたは外部キーとして使用。

### 11.9 戦歴の公開範囲と表示方針
- 公開RTDBノードには、完了ゲームのサマリ、ステージごとの参加者表示名・得点・順位、およびタイトル画面用の現在Skillだけを置く。公開履歴はPlayer/Hostでゲーム単位・ステージ単位に閲覧できる。
- 他人のチケット、予想回答、個別の得点内訳、StageSkill履歴、UUID/uid、個人統計は公開しない。個人にフォーカスした戦歴ページは本人の `auth.uid` に対応する詳細だけを読めるようにする。
- Host詳細はHost allowlistだけが購読でき、アーカイブpayloadの詳細はPlayer/Screenへ返さない。
- 現在Skill値は全員分が**タイトル画面の戦績表示**で確認可能（プレイヤー一覧形式）。
- ゲーム進行中は他プレイヤーのSkill値や統計を画面に表示しない（通信節約のため）。
- 戦歴ページのパフォーマンス対応: 初期表示は集計済みサマリ、詳細はオンデマンド取得、9項目の指標は折りたたみで表示。

## 12. 残課題・今後の検討事項

1. Spark運用で厳密なサーバ時刻締切・集計再検証を必要とする場合のBlaze + Cloud Functions移行判断。
2. 結果発表アニメーションの演出時間の最終決定（実装後の調整事項）。
3. 結果発表終了時のBGM/SEフェードアウト時間の決定。
4. クライアントログのローカル保持件数の決定。
5. 大規模イベントでの負荷試験計画。
6. GAS archiveの保持期間、Spreadsheet容量上限到達時の二次アーカイブ運用フロー。
7. 静的配信元の音声ファイル合計サイズと配信レイテンシの検証（GitHub Pagesの1GB制限・100MB/ファイル制限）。
8. `save_data` および `stage_results` のarchiveカラム構造（9指標のカラム名・データ型）の確定。
9. Player/Screenの公開履歴で表示するランキング件数と、古い履歴の閲覧期限。
10. 「再集計」操作の対象範囲: RTDB確定履歴全体か、特定ゲームだけか。
