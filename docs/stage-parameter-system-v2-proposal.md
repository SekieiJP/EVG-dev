# ステージ変数体系 v2 提案

更新日: 2026-07-29

状態: 提案・未実装

対象: ステージ制作支援ツール、ゲーム設定JSON、ゲーム本体のステージ開始処理

## 1. この文書の目的

現行のステージ設定は、総階数 `N`、定員 `X`、1階あたりの上昇報酬 `P`、1階あたりの運賃 `Q` をすべて固定値で指定する。

この方式には次の問題がある。

- 同じ定員 `X=5` でも、参加者10人と50人では強制下車の起こりやすさが大きく異なる。
- 同じ報酬 `P=10` でも、10階と50階では完乗時の報酬総額が5倍違う。
- 制作者が調整したい「定員の厳しさ」「完乗の価値」「運賃の重さ」が、現在の入力欄では直接見えない。
- 階数や想定参加者数を変更すると、関連する値を制作者が手計算で調整し直す必要がある。

v2では、制作者がステージの意図を入力し、ゲーム本体がステージ開始時に実際の `X/P/Q` を解決する方式を追加する。

このセッションでは設計だけを行い、ゲーム本体、制作支援ツール、既存JSONは変更しない。

## 2. 基本方針

### 2.1 制作値と実効値を分ける

ステージJSONには、制作者が設定したルールを保存する。

- 定員は「参加者の30%」のような割合で保存できる。
- 報酬は「1階7点」ではなく「完乗時140点」のような総額で保存できる。
- 運賃は「1階2点」ではなく「全区間40点」のような総額で保存できる。

ゲーム本体はステージ開始時にルールを解決し、そのステージで使用する数値 `N/X/P/Q` を固定する。得点計算、画面表示、結果発表は、解決後の数値だけを使う。

### 2.2 固定値を廃止しない

特殊なステージでは、制作者が `X/P/Q` を固定値で直接指定できる必要がある。v2では各変数を次のどちらかで指定できるようにする。

- 数値: 現行と同じ固定値
- ルールオブジェクト: 参加者数や階数から解決する値

通常ステージではルール指定を推奨し、演出上あえて極端な値にするステージでは固定値または手動上書きを使う。

### 2.3 プレイヤーには実効値を見せる

Player、Host、Screenに表示する「定員」「上昇報酬」「運賃」は、ルール式ではなく解決後の数値とする。

例:

- 制作値: 参加者の30%
- 参加者: 24人
- 実効値: 定員8人
- 表示: `定員 8人`

制作支援ツールだけが、ルールと実効値の両方を表示する。

## 3. 変数ルール

### 3.1 総階数 N

`N` は当面、2以上の固定整数とする。

階数自体を参加者数に比例させる案は今回は採用しない。ステージの演出時間、イベント対象階、Screenの結果発表時間まで変わるため、影響範囲が大きい。

### 3.2 定員 X: 参加者数比例

推奨ルール:

```text
X = clamp(round(participantCount × ratio), min, max)
X = min(X, participantCount)
```

初期提案では丸め方式を `ceil` とする。割合で示した人数を下回る定員になりにくいためである。

例:

```text
参加者24人 × 30% = 7.2
ceil(7.2) = 定員8人
9人目が同時に乗ろうとした時点で定員超過
```

設定項目:

| 項目 | 意味 | 初期案 |
|---|---|---|
| `mode` | 解決方式 | `participantRatio` |
| `ratio` | 参加者数に対する定員割合 | `0.3` |
| `rounding` | 整数への丸め方 | `ceil` |
| `min` | 最低定員 | `1` または `2` |
| `max` | 最大定員 | 任意、通常は未指定 |

「30%で強制下車」ではなく「定員が参加者の30%」である点に注意する。実際に強制下車が発生するのは `X+1` 人以上が同じ人数判定にかかったときである。制作支援ツールでは「24人なら定員8人、9人目で超過」と併記する。

### 3.3 上昇報酬 P: 階数反比例

制作者は1階あたりの値ではなく、1階から最上階まで成功したときの報酬総額を指定できる。

```text
P = roundTo(fullRideReward / N, step)
```

例:

```text
総階数20階
完乗時報酬140点
P = 140 / 20 = 7点/階
```

総階数を40階へ変更した場合は `P=3.5` となり、完乗時報酬は約140点に保たれる。

### 3.4 運賃 Q: 階数反比例

運賃も、全区間を申告したときの運賃総額を指定できる。

```text
Q = roundTo(fullRideFare / N, step)
```

例:

```text
総階数20階
全区間運賃40点
Q = 40 / 20 = 2点/階
```

総階数を変更しても、全区間を申告するリスクを同程度に保てる。

### 3.5 丸め

`P/Q` は現行エンジンが小数を扱えるため、初期案では `0.1` 刻みの四捨五入を推奨する。

制作支援ツールは、設定した目標総額と、丸め後の実際の総額を両方表示する。

```text
目標完乗報酬: 100点
N: 12階
P: 8.3点/階
実際の完乗報酬: 99.6点
```

得点表示を常に整数にする場合は、最終得点の丸め規則も別途確定する必要がある。

## 4. ステージ開始時の解決

### 4.1 参加者数の基準

初期提案では、`stage_intro` に入る時点で現在ゲームに参加登録されているプレイヤー数を `participantCount` として固定する。

この時点で固定する理由:

- ステージ説明画面で確定した定員を表示できる。
- 投票中の参加・離脱で定員が変動しない。
- 全端末で同じ条件を使える。
- 結果の再計算時に同じ値を再現できる。

ステージ開始後の途中参加者は、そのステージへ参加できても定員算出には含めない。次ステージから参加者数へ反映する。

### 4.2 実効値スナップショット

ゲーム本体は、解決結果を進行中roomとステージ結果へ保存する。

```json
{
  "stageId": "stage-001",
  "participantCount": 24,
  "resolvedAt": "2026-07-29T10:00:00.000Z",
  "params": {
    "N": 20,
    "X": 8,
    "P": 7,
    "Q": 2
  }
}
```

このスナップショットは設定JSONそのものには書き戻さない。設定JSONは再利用可能な制作ルール、スナップショットはそのゲームで使った確定条件として分離する。

## 5. JSONスキーマ v2案

### 5.1 バージョン

`X/P/Q` が数値だけでなくオブジェクトを受け付けるため、スキーマは `2.0.0` とする。

新しいゲーム本体はv2の数値指定とルール指定を両方読み込む。v1のJSONは数値指定のままv2として解釈可能だが、v1のゲーム本体がv2ルールを既定値へ丸めて実行することは危険なので、未対応のメジャーバージョンは明示的に拒否する。

### 5.2 記載例

```json
{
  "schemaVersion": "2.0.0",
  "gameMeta": {
    "title": "割合定員サンプル",
    "description": "参加者数比例と完乗総額を使うゲーム",
    "createdAt": "2026-07-29T10:00:00.000Z"
  },
  "parameterPolicy": {
    "participantCountBasis": "registeredPlayersAtStageStart",
    "resolveAt": "stage_intro"
  },
  "stages": [
    {
      "stageId": "stage-001",
      "name": "バランス型",
      "params": {
        "N": 20,
        "X": {
          "mode": "participantRatio",
          "ratio": 0.3,
          "rounding": "ceil",
          "min": 2
        },
        "P": {
          "mode": "fullRideTotal",
          "total": 140,
          "rounding": {
            "method": "nearest",
            "step": 0.1
          }
        },
        "Q": {
          "mode": "fullRideTotal",
          "total": 40,
          "rounding": {
            "method": "nearest",
            "step": 0.1
          }
        }
      },
      "events": []
    }
  ]
}
```

### 5.3 固定値との混在

一部だけ固定することもできる。

```json
{
  "params": {
    "N": 20,
    "X": {
      "mode": "participantRatio",
      "ratio": 0.25,
      "rounding": "ceil",
      "min": 2
    },
    "P": 10,
    "Q": {
      "mode": "fullRideTotal",
      "total": 50,
      "rounding": {
        "method": "nearest",
        "step": 0.1
      }
    }
  }
}
```

固定値は制作者の自由度を残すために必要だが、制作支援ツールでは「階数変更時に完乗総額も変わる」ことを警告する。

## 6. 制作者に見せる指標

制作支援ツールでは、`N/X/P/Q` だけでなく次の設計指標を常時表示する。

### 6.1 完乗指標

```text
完乗報酬 = N × P
全区間運賃 = N × Q
完乗純得点 = N × (P - Q)
```

### 6.2 損益分岐

全区間を申告した場合に、運賃を回収するために必要な成功階数:

```text
損益分岐成功階数 = N × Q / P
損益分岐成功率 = Q / P
```

イベント得点と倍率は含めない基礎値として表示する。

### 6.3 均等配分

エレベーターが持つ「成功可能な階数枠」は次の通り。

```text
総容量階数 = N × X
1人あたり均等成功階数 = N × X / participantCount
```

各プレイヤーが均等成功階数だけを申告し、その全区間に成功したと仮定する場合:

```text
均等配分純得点 = (N × X / participantCount) × (P - Q)
```

全員が最上階まで申告し、成功枠だけが均等に配分されたと仮定する場合:

```text
全員完乗狙い期待点 = (N × X / participantCount) × P - N × Q
```

この2つは意味が異なるため、制作支援ツールでは分けて表示する。

### 6.4 この体系で得られる正規化

定員比率を `r`、完乗報酬を `R`、全区間運賃を `F` とし、丸め誤差を無視すると次の関係になる。

```text
X / participantCount ≒ r
P = R / N
Q = F / N

均等配分純得点
= (N × r) × ((R - F) / N)
= r × (R - F)
```

つまり、参加者数と階数が変わっても、定員比率・完乗報酬・全区間運賃が同じなら、均等配分時の点数感はおおむね同じになる。

これがv2変数体系の主要な利点である。

## 7. 制作支援ツール案

以下の3案は排他的ではない。最終的には、案1を基本入力、案2を自動調整オプション、案3を常設プレビューとして同じ画面に置く構成を推奨する。

### 案1: 目標総額で作る基本モード

制作者が直接入力する項目:

| 入力欄 | 例 |
|---|---:|
| 総階数 | 20階 |
| 定員方式 | 参加者数比例 |
| 定員割合 | 30% |
| 最低定員 | 2人 |
| 完乗時の報酬総額 | 140点 |
| 全区間の運賃総額 | 40点 |
| 丸め単位 | 0.1点 |
| プレビュー参加者数 | 24人 |

入力欄の直下に、次のような結果を表示する。

```text
参加者24人の場合
定員8人 / 9人目で超過
上昇報酬7点/階
運賃2点/階
完乗純得点100点
均等配分純得点33.3点
全員完乗狙い期待点6.7点
```

長所:

- 現行の `N/X/P/Q` と対応関係が分かりやすい。
- 階数を変更しても完乗時の点数感を維持できる。
- 制作者が高得点ステージを意図的に作りやすい。

この案を初期実装の基本モードとして推奨する。

### 案2: 均等配分目標から自動調整するバランスモード

「参加者がエレベーターを公平に分け合った場合、1人あたり何点程度にしたいか」を入力する。

入力:

- 定員割合 `r`
- 均等配分の目標純得点 `S`
- 全区間運賃 `F`

完乗報酬 `R` は次で自動計算する。

```text
S = r × (R - F)
R = F + S / r
```

例:

```text
定員割合 r = 0.30
均等配分目標 S = 30点
全区間運賃 F = 40点

完乗報酬 R = 40 + 30 / 0.30 = 140点
```

画面案:

- `自動バランス` トグル
- `均等配分の目標点` 数値入力
- `運賃の重さ` 数値入力
- 自動計算された `完乗報酬` 表示
- `手動で上書き` ボタン
- `報酬補正` スライダー（例: -30%〜+100%）

報酬補正により、「定員が厳しいので高報酬」「最終ステージなので派手に高得点」といった制作者の意図を残す。

長所:

- 参加者数と階数の違いを越えて基準点を揃えやすい。
- 数学的な調整をツールに任せつつ、最後は制作者が崩せる。

注意:

- 自動計算の結果だけを見せると、制作者が何を調整しているか分かりにくい。
- 必ず計算根拠と完乗報酬を同時表示する。

### 案3: 参加者数・戦略別シナリオプレビュー

入力値を変えるたびに、右側のプレビューパネルを更新する。

参加者数の比較:

| 参加者 | 定員 | 超過開始 | 実効定員率 |
|---:|---:|---:|---:|
| 10 | 3 | 4人目 | 30.0% |
| 24 | 8 | 9人目 | 33.3% |
| 31 | 10 | 11人目 | 32.3% |

得点シナリオ:

- 1階だけ成功
- 半分の階を申告して完走
- 全区間を申告して完走
- 均等配分相当だけ申告して完走
- 全員が全区間を申告し、成功枠を均等配分
- 途中で強制下車

表示方法:

- 参加者数プリセット: 10 / 20 / 30 / 50人
- 任意参加者数入力
- 得点の棒グラフまたは小さい比較表
- 損益分岐階をフロアバー上に表示
- 現行ステージと前後ステージの完乗純得点を比較

長所:

- 数式を理解しなくても、ゲーム中の感触を予測しやすい。
- 極端な設定や丸めによる歪みを見つけやすい。
- 複数ステージ全体で得点インフレを確認できる。

## 8. 推奨画面構成

初期実装では次の構成を推奨する。

```text
左: 制作入力
  総階数
  定員方式・割合
  得点方式
  完乗報酬
  全区間運賃
  自動バランス

中央: 実効値
  想定参加者数
  定員 / 超過開始人数
  1階あたりP/Q
  完乗純得点
  均等配分純得点
  損益分岐

右: シナリオ比較
  参加者数別テーブル
  戦略別得点
  前後ステージとの比較
```

通常は目標総額を入力する。自動調整を使いたい場合だけ「均等配分の目標点」を有効にする。さらに細かく作り込みたい制作者は固定値または手動上書きを使う。

## 9. 実装時に必要な変更

このセッションでは実装しない。実装時には少なくとも次が必要になる。

- 制作支援ツールの `X/P/Q` 入力を固定値とルール指定の切替式にする。
- JSON import/exportをスキーマv2へ対応させる。
- ゲーム本体に `resolveStageParams(stage, context)` 相当を追加する。
- `stage_intro` 開始時に参加者数を固定し、実効値をroomへ保存する。
- Player、Host、Screen、得点エンジンが実効値を参照するようにする。
- 結果および履歴に実効値と解決時参加者数を保存する。
- Firebase RTDB Rulesを、ルールオブジェクトと実効値スナップショットに対応させる。
- v1 JSONの移行と、未対応メジャーバージョンの拒否を実装する。
- 固定値、割合定員、階数反比例、丸め、途中参加、再読み込み、再集計のテストを追加する。

## 10. 未解決の質問

1. 定員割合の既定丸めは `ceil` でよいか。`floor` や四捨五入を選択可能にするか。
2. 最低定員の既定値は1人か2人か。
3. 参加者数は `stage_intro` 開始時の現在ゲーム参加者で固定してよいか。
4. ステージ開始後の途中参加者をそのステージの投票へ参加させるか。参加させる場合も定員は固定したままでよいか。
5. `P/Q` は0.1点刻みを許容するか。プレイヤー向け得点表示と最終得点の丸め規則をどうするか。
6. 「均等配分純得点」は、均等階数だけ申告する想定を基準にしてよいか。「全員完乗狙い期待点」も同じ重要度で表示するか。
7. 自動バランスの基準値をゲーム全体で共通設定するか、ステージごとに設定するか。
8. イベント倍率・加点を含めた期待値シミュレーションを初期実装へ含めるか。初期版では基礎得点だけを推奨する。

## 11. 現時点の推奨

- JSONスキーマは `2.0.0` とする。
- `X/P/Q` は数値またはルールオブジェクトを受け付ける。
- 通常制作は「定員割合・完乗報酬・全区間運賃」を基本入力にする。
- 自動バランスは「均等配分の目標純得点」から完乗報酬を提案する。
- 自動調整後も完乗報酬を手動上書きできる。
- 実効値は `stage_intro` 開始時に固定し、結果へ保存する。
- 制作支援ツールでは、完乗純得点、均等配分純得点、全員完乗狙い期待点、損益分岐を常時表示する。
